# 设计决策记录：棒球主审「好球 / 坏球」判定中的信号检测论

本文件记录**为什么这样设计**。运行方式、参数表、公式与自检结果见
[`README.md`](README.md)；本文件只保留动手前的推导与取舍。

---

## 1. 为什么选这个场景

要求是"选择一个信号检测论场景，设计一个可交互网页，让用户能'玩'检测游戏"。
棒球主审判好坏球这个场景有几个很难得的性质：

1. **世界状态天然二分**：球要么经过好球区、要么没有，信号/噪声的定义不需要任何
   人为约定。
2. **有一个天然的连续物理量**可以用来操纵难度 —— 球边到好球区线的距离 ε。
   这一点最关键：它让 d′ 不是一个界面上的数字，而是"ε 与知觉噪声 σ 之比"，
   可以从数据里**反推**出来。
3. **四种结果的现实代价不对称**（一次误判好球可能直接三振、半局结束，而漏判只是
   让投手少得一个好球），这给"操纵判断标准 c"提供了场景内真实的动机，而不是
   硬凑一个滑块让人故意偏心。
4. 视觉刺激全靠 Canvas 画，助教 clone 后一定跑得起来。

## 2. 判定规则：从规则原文出发

### 2.1 擦到就算好球（第一版设计在这里是错的）

棒球规则原文：*any part of the ball passes through any part of the strike zone*。
**球的任何一部分经过好球区的任何一部分，就是好球。** 球心在好球区外但球体压线、
甚至只是相切，同样算好球。

第一版实现把"球心是否落在好球区内"当作判据，这是错的 —— 它相当于把好球区缩小了
一个球半径。正确做法：

```
球经过好球区  ⟺  球心到好球区矩形的最短距离 ≤ 球半径 r
```

于是可以把判定改写成一个**只关于球心**的条件：把矩形向四周外扩 r，得到一条
外部边界（程序内部用它来生成试次，**不画出来**），球心落在这条线内侧就是好球。

```
内部边界位置 = 好球区边界 + r          r = 1.45″（球直径 2.9″）
信号试次：球心在内侧 ε  →  球边压过好球区线 ε    →  好球
噪声试次：球心在外侧 ε  →  球边离线还有空隙 ε    →  坏球
```

这一步同时解决了两件事：

- 判定完全忠实于规则原文；
- ε 仍然是一个标量，SDT 的 `d′ = 2ε/σ` 推导完全不受影响。

画面上**只画好球区这一条白线**。判据是"球有没有碰到框"，而反馈阶段会把整颗球画在
真实位置，擦没擦到一眼可见 —— 再画一条抽象的球心判定线只会让画面变乱、让人误以为
要判断的是球心。（第一版确实画了两条线，实测观感过于臃肿，已改成单线。）

> 一个必须写进报告的诚实说明：球心一旦进入好球区内部，"压线深度"就饱和在 r 上
> （因为此时球与好球区已经完全重叠）。所以在 L1、L2 这类 ε > r 的等级上，
> ε 的直观含义是"球边到好球区线的那一小段距离"：好球 = 压线深度，坏球 = 空隙。

### 2.2 三维简化为平面

真实好球区是本垒板上方的一个**立体**区域。本实验按规模简化为**一个平面**
（球穿过本垒板前缘平面时的截面）。简化之后，"球体与立体区域相交"就变成平面上的
"圆盘与矩形相交"，即上面那个距离判据。这一简化在 README 的"已知局限"里明确声明。

### 2.3 好球区尺寸

| 项目 | 取值 | 依据 |
|---|---|---|
| 宽度 | 17″ = 本垒板宽度 | 棒球规则 |
| 高度 | 0.115 × 打者身高(cm) | MLB Statcast 平均 `sz_bot ≈ 19.2″`、`sz_top ≈ 41″`（对应约 188 cm 打者 → 21.8″），21.8 / 188 ≈ 0.116 |
| 球半径 | 1.45″（直径 2.9″） | 棒球规格 7.3–7.5 cm |

打者身高可在 170–195 cm 间切换（19.55″–22.43″），与真实规则一致。

### 2.4 只投擦边球

正中好球区或明显偏低的球不构成检测问题，测得的信息量为零。因此只投**球心离
好球区线 ±3″ 以内**的球 —— 这也正是真实棒球里最常发生争议的"压线球"。

## 3. 难度怎么操纵：σ_ext 与 ε

### 3.1 心理量模型

```
ŷ = y_true + 噪声                     y_true = 球边到好球区线的符号距离
信号：y_true = +ε   噪声：y_true = −ε   判定：ŷ > k 时判好球

d′ = 2ε / σ      （只与 ε、σ 有关，与判断标准 k 无关）
c  = k / σ       （只与判断标准有关）
β  = exp(d′·c)
```

### 3.2 为什么必须注入外部噪声（这里也是第一版的隐患）

如果显示是像素完美的，被试的知觉噪声 σ 会趋近 0、d′ 冲到天上，实验完全失去
测量能力。解决办法是心理物理学的**外部噪声范式**（Lu & Dosher, 1998）：
在每个试次给球的**显示位置**叠加一个已知大小的随机偏移。

```
2D 显示位置 = 真实位置 + N(0, σ_ext²)          σ_ext = 1.0″

σ_总² = σ_ext² + σ_自己²
d′_上限 = 2ε / σ_ext                            （理想观察者）
σ_自己 = sqrt(max(0, σ_总² − σ_ext²))           ← 无法直接观测的心理量
```

三个实现细节决定了数学是否干净：

1. 外部噪声是**每试次抽取一次并固定**的，**不是**逐帧抖动。逐帧抖动会被视觉系统
   在时间上平均掉，无法有效提高 σ；固定的随机偏移才是标准的外部噪声范式。
2. 因此显示位置的方差**恰好**等于 σ_ext²。
3. 球的柔边是固定 2px 的渲染细节，各难度一致，方差贡献约 2%，可忽略。

**副产品**：σ_自己 成了整个实验最有分量的输出 —— 物理上只操纵了 ε，
一个不可观测的心理量被算了出来。这正是信号检测论作为测量工具的价值。

### 3.3 难度等级表

| 等级 | ε | 直观参照 | d′ 上限（σ_ext = 1.0″） |
|---|---|---|---|
| L1 极明显 | 3.0″ | 约一个球直径 | 6.0 |
| L2 明显 | 2.0″ | 约 2/3 球直径 | 4.0 |
| **L3 基准（默认）** | **1.0″** | **约 1/3 球直径** | **2.0** |
| L4 困难 | 0.6″ | 约 1/5 球直径 | 1.2 |
| L5 极限 | 0.3″ | 极微小的偏差 | 0.6 |

默认 L3 的 d′ 上限 = 2.0，既不是天花板（>4）也不是瞎猜（<0.5），
是可靠测量分辨力的窗口。每球 ε 再在基准值 ±20% 内浮动，避免记住固定偏移。

### 3.4 沿边界内缩量 = 3σ_ext

每个试次只有一条"参照边界"，但球在垂直于该边界的另一个坐标上仍可能靠近相邻边界。
内缩量若太小，1″ 的显示噪声就足以把球推到相邻边界之外，试次就变成"跨两条边界的
模糊试次"，把无关混淆混进 d′。

第一版取 1.5″，实测「垂直 vs 水平」两组 d′ 相差 0.87 vs 2.79，明显被污染。
改为 **3.0″ = 3σ_ext** 后收敛到 1.57 vs 1.92，混淆被清掉。

## 4. 判断标准 c 怎么操纵

用场景化的三档「执法风格」，动机来自第四节的代价不对称：

| 风格 | 指示语 | k | c 方向 |
|---|---|---|---|
| 打者友好（严抓） | "宁可漏判好球，也不能误判坏球" | k > 0 | **c > 0**（保守，偏"判坏球"） |
| 中立 | "只按你看到的位置判" | k = 0 | c ≈ 0 |
| 投手友好（宽松） | "关键局面，边缘的球也请判好球" | k < 0 | **c < 0**（冒进，偏"判好球"） |

> **c 的方向约定**最容易讲反：标准 SDT 中 **c > 0 表示保守**（偏向报告"无信号"）；
> 本场景"是" = 判好球，所以 c > 0 = 倾向判坏球 = 打者友好／严抓。
> 结果页会把这个方向直接写出来。

## 5. 两个方法学细节

### 5.1 超时试次不能算"判坏球"

标准 SDT 要求每个试次都有二择一反应，超时试次在数学上无法归入 2×2 表。
本实现默认**单独记为「未响应」并从 SDT 计算中剔除**，只报告超时率；
配置项 `timeoutPolicy` 可切换为 `asNo` 用于对比。

若直接把超时当作"判坏球"，会人为抬高 P(Miss) 与 P(CR)、压低 P(Hit)，
把**反应速度**的差异错误地算进 **d′** 里。

### 5.2 极端比例必须修正

P(Hit) = 1 或 P(FA) = 0 时 `z(1) = +∞`、`z(0) = −∞`，d′ 直接发散。
这是 SDT 实现中最常见的 bug。默认使用 **Hautus (1995) 对数线性修正**
`P = (count + 0.5)/(N + 1)`，结果页可一键切换为 `1/(2N)` 或不修正来对比。

### 5.3 z(p) 的实现选择

用 Wichura (1988) 的 **Algorithm AS 241**（R 语言 `qnorm` 所用算法），
而不是"Acklam 近似 + Halley 迭代精修"。原因：AS 241 不依赖 Φ 自身的精度，
在中部区域对 p = 0.5 精确返回 0；Acklam + Halley 方案会继承 Φ 的约 1.5e-8 误差，
导致 `z(0.5) = −3.8e-8` 这种虽无害但难看的结果。

## 6. 为什么模式 B 必须复用刺激

ROC 曲线是"同一分辨力下改变判断标准"得到的轨迹。模式 B 让被试跑三局不同执法风格，
每局给一个 ROC 点。但如果每局都重新随机生成球的位置，两点之间的差异就**既包含
判断标准的效应，也包含抽样波动** —— 把这些点连成 ROC 就是把噪声当成效应。

因此：**只改执法风格、其它条件不变时，程序自动复用上一局的随机种子**，
让两局面对完全相同的一批球。结果页会写明"本局复用了上一局的刺激序列（种子 xxx）"。

程序还在收集模式 B 的 ROC 点时**按随机种子分组**，只取局数最多的那一组，
避免把不同刺激序列下的局（例如模式 A 跑过的那一局）混进同一条曲线。

一条经验 ROC 还必须用两个极端切点闭合：判据最严时 (0, 0)（从不判好球），
判据最松时 (1, 1)（总是判好球）。`SDT.math.auc()` 会自动补上这两个端点，
否则算出来的只是"部分面积"，是个没有意义的数值。

## 7. 界面设计

主审视角：从捕手后方看向投手。竖直构图（从下往上）：
地面 → 打者小腿/大腿（膝下缘以上是好球区）→ 好球区 → 头顶以上的空间留给远景投手
与看台。这符合真实主审视角：投手很小、出现在好球区**上方**的外野背景里。

视觉要点：

- **透视感**：好球区在近处（大），投手在远处（小）；球飞近时变大 + 运动拖影。
- **判定窗口内不画球**：球已被捕手接住，不给"定格回放"的机会。这是难度的一部分，
  也符合真实。
- **手套停在好球区中心**：模拟真实捕手的 framing 行为，同时避免泄漏落点。
- **反馈极简**：只画两样东西 —— 球在**真实位置**（整颗，叠在好球区上，"好球还是坏球"
  一眼可见），以及球边到好球区线的那一小段 ε；再加一句「✓ 判断正确 / ✗ 误判」。
  刻意**不画**任何球心标记（球本身就是判据，标个中心点只会让人以为要判球心），
  也**不画**"你看到的位置"（真实位置 + 外部噪声那个虚影）—— 反馈只需要说清
  "真实发生在哪里"，再叠一层虚影只会让画面变乱。结论也不必重复好球/坏球。
- **只画一条线**：好球区画成一条干净的白线（外加一圈深色描边，保证压在明亮草皮上
  也看得清）。第一版曾额外画一条"球心判定线"，实测观感过于臃肿，且容易让人误以为
  要判断的是球心 —— 已去掉，ε 改用反馈阶段的一小段短粗线直接标出。

界面整体走**明亮简洁**路线：说明性内容全部折叠，主页只留设置表单与一个开始按钮。

## 8. 技术架构

### 8.1 必须能在 `file://` 下双击运行

| 陷阱 | 后果 | 对策 |
|---|---|---|
| `<script type="module">` / `import` | CORS 错误，脚本全部不执行 | 全部使用传统 `<script src>`，IIFE 隔离，只挂 `window.SDT` |
| `fetch()` 读本地文件 | 被拦截 | 配置与数据全部内联在 `.js` 里 |
| 引用外部 CDN | 断网或墙掉就白屏 | 零外部依赖，图表全部 Canvas 手绘 |

### 8.2 文件结构

```
index.html              页面骨架
css/style.css           样式
js/config.js            ① 参数（好球区几何、难度表、P(S)、风格、时间、配色）
js/sdt.js               ② SDT 数学（Φ / φ / z / 修正 / d′·c·β·σ / ROC / 回归）
js/trial.js             ③ 试次生成（精确 P(S)、边界分层、ε 浮动、外部噪声）
js/stats.js             ④ 计数、分组、信心评级 ROC、会话历史
js/scene.js             ⑤ Canvas 场景
js/charts.js            ⑥ 手绘图表
js/export.js            ⑦ 数据导出
js/game.js              ⑧ 主控状态机
tools/selftest.js       数值自检（Node）
tools/domtest.js        无浏览器集成自检（Node）
```

### 8.3 自检设计

`tools/domtest.js` 用一套极简假 DOM / 假 Canvas 把 8 个脚本按 `index.html` 的顺序
加载起来，驱动 `requestAnimationFrame` 跑完三整局。它能抓出：

- 语法错误；
- **`game.js` 引用了 `index.html` 里不存在的元素 id**（纯前端项目最容易漏、又最难
  自查的一类错误，本项目里出现过一次，被它当场抓住）；
- 状态机卡死 / 试次丢失 / 记账重复；
- 场景几何退化（好球区被拉伸、极端球跑到画布外、打者挡住好球区）。

它**不能**替代在真实浏览器里看画面效果，只能保证程序逻辑跑得通。
